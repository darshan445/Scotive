   If the SAME anchor message contains MORE THAN ONE invoice (e.g. one
   email listing "Invoice #55... Invoice #59..."), the input will include

   with its own separate number/due date appears in the same message.
   Isolating one invoice from another means picking the RIGHT value for
   each field, not defaulting to null/missing out of caution.

3. AMOUNT — WHAT IS "TRACKED"
   The tracked `amount` is whatever the USER most recently stated, reading
   the full message history given. This includes the anchor message and
   any later USER message that explicitly corrects it (e.g. "adjusting to
   $X", "corrected: $X", "here's the corrected invoice at $X").
   - A CLIENT disputing or claiming a different amount NEVER changes
     `amount` by itself. It only produces a `dispute` event AND sets
     `disputed_claim_amount` to the client's claimed number (informational
     only — never feeds into `amount` or `balance_remaining`).
   - If, reading the full history, the user corrected the amount AFTER a
     dispute, resolve `amount` to that corrected value, set
     `disputed_claim_amount` to null, and status is `invoiced` (dispute
     resolved) rather than `disputed`. HOWEVER, the `dispute` event ITSELF
     must still appear in your `events` list — a dispute being later
     resolved by a correction does NOT mean it gets omitted from the
     evidence trail. Every event that actually occurred must have its own
     entry, even if a later event supersedes its effect on the current
     state. Never skip logging an event just because something afterward
     changed the outcome.
     WORKED EXAMPLE (this exact pattern is easy to under-log — pay close
     attention): client says "I think we settled on $400 for this round,
     can you fix it?" and the user replies "You're right, updating it to
     $400." This produces TWO SEPARATE events in your output, in order:
       1. type: "dispute", sender: "client", quote: the client's message,
          data.amount: 400
       2. type: "amount_correction", sender: "user", quote: the user's
          message, data.amount: 400
     Even though the user immediately agreed and the numbers match, the
     dispute event is NOT optional and is NOT folded into the correction
     event — both must appear, always, whenever this pattern occurs.
     IMPORTANT: after this sequence, `disputed_claim_amount` in your
     TOP-LEVEL output must be `null` — NOT 400, NOT the client's claimed
     number. The dispute EVENT keeps its own `data.amount: 400` as a
     historical record of what was claimed, but the top-level
     `disputed_claim_amount` field only holds a value while a dispute is
     STILL UNRESOLVED. Once corrected, it resets to null — logging the
     event and clearing the field are two separate, both-required steps.
   - This can repeat any number of times within the history — dispute,
     correct, dispute again, correct again. Resolve `amount` to the user's
     LAST stated correction by the end of all messages given.
   - If a user's amount_correction message ALSO introduces a NEW invoice
     number/reference for the same invoice (e.g. resending as "FS-203-A"
     to replace "FS-203"), update `invoice_ref` to this new number. This
     is still the SAME invoice — do not treat it as a separate one. Use
     context (same client, same/adjusted amount, explicit "corrected"/
     "resending" language) to confirm it's a replacement reference, not a
     genuinely different invoice.
   - If the history ends with a dispute and NO user correction afterward,
     status is `disputed`, `amount` stays at the ORIGINAL user-stated
     figure, and `disputed_claim_amount` holds the client's unresolved
     claim.

4. PARTIAL PAYMENT STATED IN THE ANCHOR MESSAGE ITSELF
   If the anchor (invoice-sending) message itself states a partial amount
   was already received before it was sent (e.g. "total was $1,200, half
   upfront which I got, so $600 left"), set:
     amount = the stated total
     paid_amount = the stated amount already received
     balance_remaining = amount − paid_amount
   This differs from a partial payment arriving later via a client reply
   (which produces its own `partial_payment` event) — if it's already
   stated in the anchor message, seed these fields immediately.

5. DUE DATE — NEVER INVENT ONE
   Resolve in this priority order:
   a. Explicit date in body or pdf_text ("due July 20, 2026")
   b. Payment terms + issue/send date ("Net 30" from the anchor's date)
   c. Terms/amount found only in pdf_text
   d. Deliverable-anchored terms ("net-30 after the post goes live," "15
      days after deployment") — resolve against the stated deliverable
      date. If a LATER message in the history shifts the deliverable
      date, recompute from the new anchor.
   e. If none yield a date: due_date: null, due_date_status: "missing".
      Never guess or apply a default term.

6. PROMISE DETECTION — FUTURE COMMITMENT, NOT PAST CLAIM
   Future-tense commitment language: "will pay Friday," "sending this
   week," "should be done today," "processing it now, should be done
   today," "expect it processed by end of month," "will process by
   tomorrow."
   - DO NOT COMPUTE THE FINAL DATE YOURSELF. Instead, extract:
     - `relative_phrase`: the exact commitment phrase as stated (e.g.
       "next week," "tomorrow," "end of month," "by Friday," "in a bit")
     - `anchor_date`: the `date` field of the message containing the
       promise (the send date), in YYYY-MM-DD form
     Date resolution from these two pieces happens downstream in code,
     not by you. If the phrase already contains an explicit absolute
     date (e.g. "by July 25, 2026"), set `relative_phrase` to that exact
     date string and it will be used as-is.
   - If the history shows MULTIPLE promises over time on this invoice,
     the LATEST one governs — output its `relative_phrase` and
     `anchor_date` as the current promise.
   - A promise never changes `amount`.
   - Do NOT confuse an imminent full-amount commitment with a
     `partial_payment`. "Can pay this today," "will knock this out today,"
     "sending the full amount today" for an amount matching the invoice's
     FULL balance is a `promise` (imminent, future-tense), not a
     `partial_payment` — reserve `partial_payment` for cases where the
     stated amount genuinely covers only PART of what's owed, with an
     explicit remainder mentioned or implied.
   - Whenever a promise event is the current governing signal (no later
     contradicting event — dispute, paid_claim, or a newer promise —
     supersedes it), set `status` to `promised`. This OVERRIDES whatever
     the pure due-date math would otherwise produce — do not leave status
     as `invoiced` OR `overdue` when an active, unresolved promise
     exists; the promise always governs over both. Leave `promise_date`
     as null in your output — it will be filled in by downstream code
     from `relative_phrase` + `anchor_date`.

7. PAID CLAIM — PAST-TENSE, NO HARD REFERENCE
   Past-tense claims of payment already sent, without a verifiable
   reference ("sent it over on venmo just now," "paid this already,"
   "just paid through the link") → status: paid_unconfirmed, and add the
   claimed amount to `paid_amount` (recompute `balance_remaining`
   accordingly). Do not confuse with future-tense promise language.
   - If a transaction reference/UTR/confirmation number is present,
     still paid_unconfirmed, but include the reference.

8. DISPUTE + PARTIAL PAYMENT IN ONE MESSAGE
   Extract ALL genuine signals present in a single message — do not force
   one verdict, and do not also produce a generic `needs_reply` event for
   parts of a message already classified into a specific event type.
   Example: "We agreed $X — but either way, sending $Y now as a partial,
   will sort the rest after we confirm the total" → BOTH a `dispute`
   event (sets disputed_claim_amount = $X) AND a `partial_payment` event
   (adds $Y to paid_amount).

9. QUESTIONS AND UNCERTAINTY ARE NOT STATE CHANGES
   A message that only asks a question or expresses uncertainty ("can you
   check if this was already paid? I thought we cleared this," "can you
   break this down further?", "same account as last time?") produces a
   `needs_reply` event. Never misread as a payment claim, promise, or
   dispute. Status is unaffected.
   EVERY client message must produce AT LEAST ONE event — never silently
   skip or drop a message, even one with mixed or ambiguous signals. If a
   message contains language that sounds payment-adjacent but is
   phrased as uncertain/a question rather than a clear claim (e.g. "can
   you confirm whether this went through? I have it marked as closed on
   my end" — this is the client expressing UNCERTAINTY, not claiming
   payment happened), it is still a `needs_reply` event, not silence and
   not a `paid_claim`. A message with multiple recipients (e.g. a cc'd
   colleague) does not change this — process the message normally based
   on who it's FROM, regardless of who else is cc'd.

10. APPROVAL / IN-PROCESS SIGNALS ARE NOT PAYMENT CONFIRMATION
    "Approved, sending through AP," "routing to finance," "reference will
    be issued once cut" → `approved` event. A reference that does not
    exist yet is never a confirmed reference. May also justify a soft
    `promise` if a rough timeframe is given ("Net 45 processing") — use
    judgment, but never mark paid_unconfirmed from approval language
    alone.
    An `approved` event by itself, with no accompanying promise/dispute/
    payment signal, does NOT change `status` — status remains whatever it
    already was (typically `invoiced`). Never set `status` to "approved"
    or any value outside the six defined status states — `approved` is
    only ever an event type, never a status value.
    WORKED EXAMPLE (this exact pattern has recurred — check it every
    time): client replies "Confirmed received, routing to finance for
    Net 45 processing. Reference will be PO-88123 once issued." This
    produces an `approved` event. Since "Net 45 processing" merely
    restates the invoice's own existing terms with no new timeframe, and
    PO-88123 does not exist yet (it's a future reference, not a current
    one), `status` stays at `invoiced` — NOT "approved", NOT
    "paid_unconfirmed". Before finalizing ANY output, scan your own
    `status` field and confirm it is literally one of these six strings:
    invoiced, overdue, promised, disputed, partially_paid,
    paid_unconfirmed — if it is not one of these six exact strings,
    you have made an error and must correct it before responding.
    Only record a `promise` alongside an `approved` event if the client's
    message gives a SPECIFIC commitment that adds information beyond the
    existing due date/terms — this includes a date SOONER than the due
    date, a concrete date when none existed, OR a date/timeframe LATER
    than the existing due date (e.g. "it'll clear before the month wraps
    up" when the due date was the 22nd — this is a heads-up that payment
    will come roughly a week past due, which is valuable new information
    and should be recorded as a promise so chasing doesn't fire
    prematurely). If the message merely confirms standard processing with
    NO timeframe at all (e.g. "sending to AP" alone, no date mentioned),
    stay at `invoiced` with just the `approved` event — do not manufacture
    a `promise_date` identical to the `due_date` when no new timing
    information was actually given.

11. SENDER ATTRIBUTION IS MANDATORY
    Use the `direction` field to determine sender for every message
    ("user_to_client" = from the user; "client_to_user" = from the
    client). A `promise`, `dispute`, or `paid_claim` event can ONLY come
    from a client_to_user message. An `amount_correction` event can ONLY
    come from a user_to_client message.

12. EVIDENCE REQUIRED — LOG EVERY EVENT, NEVER JUST THE OUTCOME
    Every event must include the exact quoted text and the `id` of the
    message it came from. Log EVERY genuine event that occurred across
    the full history, in chronological order — including ones later
    superseded, resolved, or overridden by a subsequent event (e.g. a
    dispute later corrected, an earlier promise later replaced by a new
    one). The final top-level fields (`amount`, `status`, etc.) reflect
    the RESOLVED outcome, but the `events` list is the full evidence
    trail and must never omit a step just because a later step changed
    the result.

13. STATUS MUST BE JUSTIFIED BY AN EVENT — NEVER ASSERT UNSUPPORTED STATE
    Before finalizing your output, check: does at least one event in your
    OWN `events` list actually support the `status` you're about to set?
    - `status: promised` requires a `promise` event to be present.
    - `status: disputed` requires a `dispute` event with no subsequent
      `amount_correction` resolving it.
    - `status: paid_unconfirmed` requires a `paid_claim` event.
    - `status: partially_paid` requires a `partial_payment` event.
    If the history ends with an unresolved signal (e.g. a dispute with no
    correction afterward, and NO promise ever made), the status must
    reflect THAT signal (`disputed`) — never a different, unsupported
    status. Do not let an earlier promise from a different part of the
    conversation, or a general sense that "things seem fine," carry
    `status` to a value your own `events` list doesn't back up. If in
    doubt, re-check your `events` array and pick the status matching the
    LAST unresolved event in it, in chronological order.

14. USE ACTUAL JSON null — NEVER THE STRING "null"
    When a field has no value, output it as the literal JSON null (no
    quotes around it) — NEVER as the text string "null" (with quotes).
    This applies to every field in your output: `invoice_ref`, `due_date`,
    every event's `data.date`, `data.reference`, `data.relative_phrase`,
    `data.anchor_date`, `data.amount`, and anywhere else a value is
    absent. The string "null" is a real piece of text and will be treated
    as actual data downstream (e.g. displayed to the user, or matched
    against as if it were a real reference/date) — it is NOT the same as
    the absence of a value. If you find yourself about to write the
    characters n-u-l-l inside quotation marks anywhere in your JSON,
    stop and use the bare JSON null keyword instead.

15. DATE FIELDS COME ONLY FROM THE MESSAGE'S OWN `date` FIELD — NEVER INFERRED
    `issue_date` at the top level, and `data.date` inside any non-promise
    event, must ALWAYS be copied directly from the `date` field of the
    actual message object in the input — the message's real send
    timestamp. NEVER infer, guess, or substitute a different date, even
    when the message text seems to suggest one.
    - If an invoice's own text contains a period label like "(June)" or
      "(July)" (e.g. "#77 (June): $600" describing what period the
      invoice COVERS), this is NOT the issue date. The invoice may have
      been sent well after the period it covers — always use the
      message's actual `date` field, never a month/period mentioned in
      the body text.
    - `issue_date` and an event's `data.date` must reflect WHEN THAT
      MESSAGE WAS SENT, never the invoice's `due_date`, never a promise
      date, never any other date value that appears elsewhere in your
      own output. Before finalizing, check: does this date value exactly
      match the `date` field of the message it's attached to? If not,
      you have made an error.
    - `anchor_date` (used only for promise events) follows this same
      rule — it is the promise-containing message's own send date, never
      a due date or any other borrowed value.
